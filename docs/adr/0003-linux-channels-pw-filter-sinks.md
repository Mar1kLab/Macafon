# ADR-0003: каналы вывода на Linux — собственные узлы-приёмники `pw_filter`

- **Статус:** принято
- **Дата:** 2026-10-11
- **Контекст PRD:** [§7](../PRD.md#7-функциональные-требования--каналы-вывода), [§12.1](../PRD.md#121-linux--pipewire-m0m2), NFR-L3
- **Связано:** виртуальный микрофон M0 — тот же приём с `pw_filter` ([linux-m0.md](../development/linux-m0.md))

## Контекст

Каждый канал микшера должен быть отдельным устройством вывода, которое видят приложения и на которое
WirePlumber может перенести их поток через `target.object`. Звук канала проходит цепочку
`EQ → NS → Compressor → Limiter → Volume` и сводится с остальными в одно реальное устройство.
PRD §12.1 оставил выбор схемы на M0: внутренний микс в одном playback-потоке или сведение силами PipeWire.
NFR-L3 требует, чтобы канал без NS не добавлял буферизации сверх цикла графа.

## Рассмотренные варианты

| Вариант | Итог |
|---|---|
| A. Пара на канал: capture-поток `Audio/Sink` + playback-поток к устройству, связь через SPSC-буфер | Отклонён: лишний quantum задержки на канал, два узла и рассинхронизация при рестартах |
| B. N узлов-приёмников и один общий playback-поток с внутренним миксом Master | Отклонён: узлы-приёмники и выходной поток не упорядочены в цикле графа, микс требует буфер в 1 quantum и общего состояния между колбэками |
| **C. Один `pw_filter` на канал: входы — порты `Audio/Sink`, выходы Macafon сам линкует с устройством** | **Выбран** |
| D. Модули PipeWire (`filter-chain`, `loopback`) | Отклонён ещё в PRD §12.1: конфиг-файлы, нет метров и параметров в реальном времени |

## Решение

Канал — узел `pw_filter` с `media.class = Audio/Sink`, `node.name = macafon_ch_<id>`, стерео-входами
`playback_FL/FR` и выходами `output_FL/FR`. Приложения линкуются к входам через WirePlumber как к обычному
приёмнику; цепочка обрабатывает буфер на месте в том же цикле; выходы демон линкует к выбранному устройству
через `link-factory` (как вход виртуального микрофона). Несколько каналов сводятся в устройстве самим
PipeWire. Master — общий множитель громкости внутри каждого канала. Каналы с префиксом `macafon_ch_`
исключены из списка выходов (OUT-004) и из собственных маршрутов.

Маршрутизация приложений — запись `target.object` (serial узла канала) в `default` metadata; демон
отслеживает потоки `Stream/Output/Audio` через registry и полные `NodeInfo`. Системный default output
(OUT-005) перехватывается через ту же схему журнала, что и default source (MIC-012).

## Последствия

- Канал без NS добавляет 0 сэмплов буферизации; задержка цепочки сообщается через `ProcessLatency` (NFR-L4).
  Проверено в приватном графе PipeWire 1.6.2 + WirePlumber 0.5: `tools/tests/mixer-smoke.py`.
- Линки каналов к устройству не пассивные: пока микшер включён, устройство не уходит в suspend. Вариант с
  `link.passive` не проверялся; влияние на питание ноутбука нужно оценить на стенде. Выключенный микшер не
  создаёт ни одного узла (CH-009).
- Метр Master — максимум пиков каналов после Master-фейдера, а не измерение на устройстве: звук приложений,
  идущий мимо Macafon (`node.dont-move`), в нём не виден.
- Потоки с `node.dont-move` / `node.dont-reconnect` не переносятся; UI показывает их как неперемещаемые.
- Правило применяется в течение ≤ 100 мс после появления потока (тик управляющего цикла). До этого поток
  успевает подключиться к каналу по умолчанию — короткий звук не в том канале возможен (см. APP-005).
